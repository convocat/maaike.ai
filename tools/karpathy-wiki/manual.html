Part AUnderstand

Concept
What the dashboard is

The dashboard is a test harness for the wiki Q&A.

It holds 55 fixed questions across seven categories (relevant, ambiguous, out-of-scope, adjacent, and two kinds of adversarial) and lets you fire them at the real wiki server. You see the answer, the retrieval trace, and the judged grounding of each claim. You score by hand; the machine judges in parallel.

The output is a record of "how good is the system right now, and did my last change make it better or worse?"

Structure
Anatomy of the screen

Three panes, one top bar.

Left sidebar

All 55 questions grouped by category. Coloured dot shows state: grey (unrun), dark-grey (run but unscored), red/amber/green (scored 1/2/3).

Centre pane

The question, expected source, streamed answer, then the Evaluation table: retrieval, knowledge-graph usage, sources cited, answer characteristics, claim verification, latency.

Right panel

Summary score (1/2/3), the 10-criterion rubric, notes, and action buttons: Run, Verify, Prev/Next.

The top bar holds the Wiki URL field (with health dot), progress counter, and five global buttons: Run all, Verify all, Report, Export JSON, Start fresh.

Principle
Three defenses against hallucination

The system cannot guarantee truth, but it makes hallucination visible, measurable, and refusable when evidence is thin.

The wiki Q&A uses three layered defenses. Understanding what each one does will tell you how to interpret what you see.

  1. Defense A — refuse when retrieval is weak. If zero topics, triples, and themes match the question, the server returns a canned refusal without calling the LLM. Zero tokens, zero hallucination risk on truly out-of-scope questions.
  2. Defense B — verify claims after the answer. A second LLM call reads the source articles and classifies every claim in the answer as verified, inferred, or unverified. Makes hallucination visible per claim.
  3. Phase 1 — LLM-as-judge across the whole test set. Run Defense B on all 55 questions to get a corpus-wide hallucination rate.

None of these suppress the answer to the user. They annotate. You are still the final ground truth.

Process
Defense A — what happens when retrieval is weak

A retrieval gate before the LLM is ever called.

  1. The server runs graph retrieval on the question.
  2. If zero topics, triples, and themes match: short-circuit.
  3. Return a canned refusal: "I don't have material on this in Maaike's garden…"
  4. No Anthropic API call is made.
  5. The dashboard shows a green banner in the Evaluation panel labelled "Defense A: retrieval refused".

This catches the worst failure mode (Claude making things up when the garden has nothing relevant) with zero cost.

Process
Defense B — what happens when you click Verify

A second LLM reads the sources and classifies each claim.

  1. The dashboard POSTs {question, answer, source_slugs} to /api/verify.
  2. The server loads the full text of the retrieved articles.
  3. A judge Claude is asked: for each factual claim in the answer, is it supported by the sources?
  4. The judge returns JSON with three buckets: verified (quote-matched), inferred (reasonable extension), unverified (no basis).
  5. The dashboard renders the counts, an overall verdict (grounded, mixed, hallucinating), and every claim colour-coded with its supporting quote.

The cost is ~$0.003 per verification. Running on all 55 is ~$0.15.

Classification
What the score values mean

Three scores. Use the one that fits the overall judgement; use the rubric for why.

1 · wrong
Any of: invents facts, attributes opinions Maaike doesn't hold, engages with an adversarial trap, or contradicts what's in the sources. One clearly fabricated sentence is enough for a 1.
2 · partial
On-topic and not wrong, but something's off: too generic, misses nuance, overstates confidence, or tonally flat. Reader can't tell the answer came from Maaike's garden specifically.
3 · correct
Grounded in the sources, accurate to Maaike's actual position, reads like her voice, invites a follow-up. Traceable to a specific article if asked.

Part BDo

Procedure
Start the eval stack

One command starts both servers and refuses to silently stack zombies.

  1. Open a terminal in the repo root.
  2. Run bash scripts/eval-dev.sh.
  3. Wait for the green "Stack is up" message.
  4. Open http://localhost:8782/eval.html.
  5. Check the coloured dot next to the Wiki URL field.
Tip — green dot = all features present; yellow = server up but outdated (restart it); red = no server.
Procedure
Run one question

See what the system does with a single prompt.

  1. Click a question in the left sidebar.
  2. Click Run in the right panel.
  3. The answer streams into the middle pane.
  4. Scroll down: the Evaluation section shows which topics matched, which triples fired, which articles went to Claude, and how long it took.
Tip — if an answer feels off, check Topics matched and Articles retrieved first. Nine failures out of ten are retrieval misses, not generation failures.
Procedure
Run the full baseline (all 55)

Creates the reference point you compare every future change against.

  1. Click Run all in the top bar.
  2. It skips questions already run. Progress shows n/55.
  3. Wait ~5 minutes. You can peek at partial results while it runs.
Tip — do this once before any system change. It becomes your before.
Procedure
Score an answer quickly

Assign the overall 1/2/3 score.

  1. Select the question.
  2. Read the answer.
  3. Click 1, 2, or 3 in the Score block, or press those keys.
  4. Click an active score button to clear.
  5. Dashboard auto-saves and advances to the next unscored question.

For what each score means, see Score meanings. For deeper thinking about how to score consistently, see the Methodology document.

Procedure
Score with the rubric

Decompose the single score into 10 concrete, actionable criteria.

  1. With a question selected, go to the Quality rubric block in the right panel.
  2. For each criterion, click ✓ (pass) or ✗ (fail). Skip criteria that don't apply.
  3. Click an active button to clear it.
  4. The summary line shows N/10 rated · P pass · F fail.
Tip — if "Invites a follow-up" fails across many questions, that's a concrete fix: tune the system prompt's closing ritual. The single 1/2/3 doesn't give you that.
Procedure
Verify claims for one answer

Runs Defense B on the current question.

  1. With a question that's been run, click Verify claims in the right panel.
  2. Wait a few seconds.
  3. The Evaluation panel grows a Claim verification section.
  4. Read the verdict: grounded, mixed, or hallucinating.
  5. Unverified claims are listed first, in red — the specific things the answer said that aren't in the sources.
Warning — low verified-count with a long answer usually means Claude padded with training-data knowledge. That's a prompt or retrieval problem, not a verification problem.
Procedure
Verify claims across the whole test set

Runs Defense B on every question that has an answer.

  1. Click Verify all in the top bar.
  2. It skips questions already verified.
  3. Roughly ~$0.15 and ~3 minutes for 55 questions.
  4. When it finishes, open Report for aggregates.
Procedure
Read the Report

Summary across all questions — pass/fail against acceptance criteria.

  1. Click Report in the top bar.
  2. Check Acceptance criteria — each row is a pass/partial/fail pill against a concrete threshold.
  3. Scroll to Failures — every question that failed, with an auto-diagnosis ("retrieval miss", "generation issue", "trap not refused").
  4. Read Next steps — generated from your current results.
Procedure
Snapshot state before changes

Save the current run as a comparable baseline.

  1. Click Export JSON in the top bar.
  2. A file downloads named eval-YYYY-MM-DD.json.
  3. Rename it to something meaningful: eval-baseline-before-prompt-tune.json.
Tip — the Start fresh button auto-exports a timestamped backup before wiping. You won't lose data to accidental resets.
Procedure
Compare before/after a system change

Did the change improve things, regress, or neither?

  1. Snapshot current state (see above).
  2. Make your change (add triples, tune system prompt, etc).
  3. Click Start fresh in the top bar (auto-backup + wipe).
  4. Re-run all 55 (see Run the baseline).
  5. Re-score (see Score an answer).
  6. Re-verify all (see Verify across the test set).
  7. Compare: did mean score go up? did unverified-claim rate go down? did any question regress from 3 → 2?
Warning — always check for regressions, not just improvements. A 1-point drop on one relevant question can negate a win elsewhere.
Procedure
Start fresh (wipe all results)

Deletes answers, scores, rubrics, and verifications with an automatic backup first.

  1. Click Start fresh in the top bar.
  2. A confirmation dialog shows how many answers and scores will be deleted.
  3. Click OK.
  4. A JSON backup downloads automatically (filename includes a timestamp).
  5. localStorage is cleared; the dashboard redraws with all dots grey.
Tip — to restore from a backup, open DevTools → Application → Local Storage → localhost:8782 → paste the exported JSON back into eval_results_v1.

Troubleshooting

Procedure
Symptom: Nothing happens when I click Run

Usually the wiki server is stuck or the button is frozen from an earlier failed call.

  1. In terminal: bash scripts/eval-dev.sh --stop
  2. Then: bash scripts/eval-dev.sh
  3. Hard-refresh the dashboard: Ctrl+Shift+R.
Procedure
Symptom: Health dot is yellow

Server is up but missing expected features (old serve.py running).

  1. bash scripts/eval-dev.sh --stop && bash scripts/eval-dev.sh
  2. Check the dot again.
Procedure
Symptom: "No knowledge-graph trace" banner

The cached result pre-dates the server's current version.

  1. Click Run in the right panel to re-run that question.
Procedure
Symptom: Smoke test reports failures

At least one check in scripts/eval-smoke-test.sh is red.

  1. Run bash scripts/eval-smoke-test.sh and read the red lines.
  2. Each failing check names exactly what's broken (port, feature flag, DOM reference, CORS).
  3. If wiki-related, restart the stack.
Definition
Glossary
Expected source The article I think the answer should cite, coded into the test set. Used for the automated "found in retrieval" check. Graph retrieval Retrieval mode when at least one topic or triple matched. Strong signal. Fallback Retrieval mode when nothing matched; the server sends the whole corpus as short snippets. Weaker signal, more hallucination-prone. Defense A Server-side refusal when retrieval finds zero matches. No LLM call. Visible as a green banner. Defense B Post-answer claim verification. A second LLM classifies each claim as verified / inferred / unverified. Rubric The 10 yes/no criteria in the right panel. Decomposes the single 1–3 score into actionable dimensions. Verdict Overall judgement from Defense B. grounded = ≥80% verified claims. mixed = 50–79%. hallucinating = <50%. Unverified claim A factual statement in the answer that the judge could not find in the source articles. Potential hallucination.
The one thing to remember — the dashboard doesn't prevent hallucination. It makes hallucination visible, measurable, and refusable when evidence is thin. You are still the final judge.
